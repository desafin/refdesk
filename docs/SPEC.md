# refdesk 스펙 v0.2

작성일 2026-11-25. 프로젝트 이름은 **refdesk**(실행 파일도 `refdesk`), UI 는 egui 로 확정했다.
구조와 모듈 간 계약은 [ARCHITECTURE.md](ARCHITECTURE.md), 작업 분할은 [PLAN.md](PLAN.md) 에 있다.

## 1. 목적

소프트웨어 기술문서 PDF 여러 개를 동시에 띄워 놓고 읽기 위한 Linux 데스크톱 뷰어.
탭·분할·여러 창으로 문서를 배치하고, 탭을 창에서 떼어 내거나 다시 붙일 수 있으며,
링크 점프·목차·세션 기억·문서 비교(diff)를 갖춘다. Rust 로 작성하고 소스는 GitHub 에 공개한다.

## 2. 전제 (고정)

| 항목 | 값 |
|---|---|
| 대상 환경 | **이 로컬 머신 한 종류**: Ubuntu 26.04.1 LTS, GNOME Shell 50.1 (Wayland 세션, XWayland 실행 중) |
| 화면 | 모니터 3대 (1920×1080 ×2, 2560×1440 ×1), 배율 모두 100% |
| 입력기 | fcitx5 |
| 하드웨어 | 32 코어, RAM 60GB, NVIDIA RTX 4070 + AMD 내장 |
| 툴체인 | Rust 1.95 (stable), 추가 apt 패키지 설치 없이 빌드 가능해야 함 |
| 대상 문서 | 소프트웨어 기술문서 PDF (텍스트·표·그림 위주, 수백~수천 쪽, 깊은 목차, 내부 교차 참조 링크 다수) |

Windows·macOS·다른 배포판·다른 데스크톱 환경은 지원하지 않으며 설계에서 고려하지 않는다.

## 3. 원칙

1. **사용자 편의가 1순위.** 구현이 쉬운 쪽과 쓰기 편한 쪽이 갈리면 쓰기 편한 쪽을 택한다.
2. **최적화는 나중에.** 메모리와 CPU 는 넉넉하게 쓴다(전체 텍스트를 메모리에 올리고, 캐시를 크게 잡는다).
   단, UI 스레드가 멈추는 것은 최적화 문제가 아니라 편의 문제이므로 처음부터 막는다.
3. **모든 기능은 찾을 수 있어야 한다.** 메뉴·우클릭·명령 팔레트 중 하나 이상에서 보이고, 단축키는 거기에 함께 표시한다.
4. **읽던 자리를 잃지 않는다.** 점프하면 돌아갈 수 있고, 닫았다 열어도 그 자리이며, 줌 때문에 화면이 비지 않는다.

## 4. 비목표

PDF 편집, 양식 입력, 전자서명, JavaScript, 멀티미디어/3D, 스캔 문서 OCR, PDF 이외 포맷(EPUB 등),
터치/태블릿 조작, 스크린리더 수준의 접근성, 클라우드 동기화.

## 5. 기술 스택

### 5.1 결정

| 영역 | 선택 | 이유 |
|---|---|---|
| PDF 엔진 | **MuPDF** (`mupdf` 크레이트 0.8.0) | 렌더링, 링크와 목적지 해석, 목차, 문자 단위 좌표, 검색을 한 라이브러리가 제공. 소스 포함 빌드라 시스템 패키지가 필요 없음 |
| UI | **egui 0.37 / eframe** + **egui_dock 0.22** | 순수 Rust(Qt·GTK 미사용). 탭+분할 도킹이 기성품. PDF 페이지처럼 직접 그리는 화면에 즉시 모드가 잘 맞음. 여러 OS 창(뷰포트) 지원 |
| Diff | **similar 3.2.1** | 임의 토큰 비교, Histogram/Patience, 시간 제한, 단어 수준 정제 |
| 저장 | JSON(세션·문서 상태) + TOML(설정), XDG 경로 | 사람이 읽고 고칠 수 있음. SQLite 는 필요해지면 |
| 보조 | `rfd`(GNOME 파일 선택기, 포털 경유), `notify`(파일 변경 감시), `directories`, `xxhash-rust`, `unicode-normalization` | |

**라이선스는 AGPL-3.0** 이 된다 (MuPDF 가 AGPL). 소스를 전부 공개할 계획이므로 문제없다.

### 5.2 검토 후 제외한 대안

| 대안 | 제외 이유 |
|---|---|
| GTK4 + libadwaita (`gtk4-rs`) | 탭을 창 밖으로 떼어 내는 기능이 기본 제공되는 유일한 후보지만, "Qt 류를 피한다"는 방침에 어긋나고 개발 패키지 설치가 필요 |
| iced | 분할(`pane_grid`)만 있고 탭/도킹은 직접 만들어야 함 |
| GPUI + gpui-component | 도킹은 있으나 OS 창 분리는 없음. API 변동이 큼 |
| Tauri + PDF.js | UI 대부분이 JS 가 되어 "Rust 로 작성" 목표와 어긋남 |
| PDFium (`pdfium-render`) | `libpdfium.so` 를 별도로 구해 배치해야 함. 스레드 안전성이 전역 잠금 방식 |
| Poppler | glib/cairo 개발 패키지 필요 |
| hayro (순수 Rust) | 렌더링 전용. 텍스트 추출·검색이 없어 선택·검색·diff 를 못 만듦 |

어떤 순수 Rust 툴킷도 "탭을 OS 창으로 분리"를 기성품으로 주지 않는다. 그래서 이 부분은 어느 쪽을 골라도 직접 구현이다.

### 5.2.1 순수 Rust UI 를 택해 얻는 것과 치르는 것

| 얻는 것 | 치르는 것 |
|---|---|
| `cargo build` 하나로 끝. 시스템 개발 패키지와 C++ 연결 코드가 없음 | 탭을 OS 창으로 떼고 붙이는 기능을 직접 만들어야 함 (GTK 는 기성 위젯) |
| UI 까지 한 언어. FFI 경계와 GObject/QObject 수명 규칙을 다루지 않음 | 입력기(한글), 끌어 놓기 같은 데스크톱 통합이 덜 성숙 |
| 페이지 위에 링크·선택·검색·diff 표시를 겹쳐 그리는 화면에 즉시 모드가 잘 맞음 | GNOME 기본 앱과 생김새가 다름 |
| 창 없이 UI 테스트 가능 (`egui_kittest`) | egui 는 0.x 라 버전을 올릴 때마다 API 가 바뀜 |
| 도킹·탭 동작을 우리 코드로 완전히 제어 | 화면을 GPU 로 그리므로 그래픽 드라이버에 의존 |

참고: PDF 엔진 MuPDF 는 C 다. cargo 가 소스째 빌드하므로 빌드 경험은 같지만, 프로그램 전체가 순수 Rust 인 것은 아니다.
UI 를 모르는 `core` 를 분리해 두므로(§8.1), 나중에 툴킷을 바꾸더라도 다시 쓰는 범위는 `app` 에 한정된다.

### 5.3 이 머신에서 실측한 것 (2026-11-25)

| 확인 내용 | 결과 |
|---|---|
| `mupdf 0.8.0` + `eframe 0.37` + `egui_dock 0.22` 빌드 | 통과 (406 크레이트, apt 설치 없음) |
| 빌드 함정 | `mupdf` 의 `system-fonts`(font-kit) 와 `eframe` 의 `system_fonts`(fontique) 가 fontconfig 를 다른 모드로 켜서 컴파일 실패 → `font-kit` 에 `source-fontconfig-dlopen` 피처를 맞추면 해결 |
| 660쪽 문서 | 열기 1.3ms, 전체 텍스트 추출(189만 자) 0.48초, 목차 31항목 |
| 117쪽 문서 | 링크 509개(내부 480개) + 텍스트 전체 스캔 0.12초 |
| 페이지 렌더링 (200% 배율) | 텍스트 페이지 0.7~21ms. 대형 스캔 이미지 페이지(4960×7016px)는 430ms |
| 스레드 | `DisplayList` 를 다른 스레드로 넘겨 래스터화 가능. `Document`/`Page` 는 만든 스레드에 묶임 |
| `egui_dock` 탭 떼어내기 | 앱 내부 플로팅 창까지만. OS 창 분리는 없음 |
| winit 0.30.13 (Wayland) | 창 위치 읽기/쓰기 불가, 파일 드롭 미구현, 창 숨기기 불가 |
| eframe | 최초 창(루트)을 닫으면 앱 전체 종료 |
| 한글 | Noto Sans CJK 설치됨. `DockState` 는 serde 직렬화 가능 |

아직 확인하지 않은 것: 실제 창을 띄운 상태의 동작 전부(탭 드래그, 한글 입력, 여러 창). 계획의 M0 에서 확인한다.

## 6. 용어

| 용어 | 뜻 |
|---|---|
| 창 | OS 창 하나 |
| 패인 | 창 안에서 분할된 영역. 탭 묶음 하나를 가짐 |
| 탭 | 뷰 하나를 담는 단위. 패인 사이, 창 사이로 옮길 수 있음 |
| 문서 | 열린 PDF 파일. 여러 뷰가 공유 |
| 뷰 | 문서 하나를 보는 상태(위치, 줌, 히스토리, 선택, 검색) |
| 위치 | (페이지, 페이지 안 x·y — PDF 포인트 단위). 화면 픽셀로 저장하지 않음 |

### 7.14 번역 (로컬 AI 모델)

## 8. 아키텍처

개요만 적는다. 모듈 지도, 타입과 함수 계약, 불변 규칙은 [ARCHITECTURE.md](ARCHITECTURE.md) 가 원본이다.

### 8.1 크레이트 구성

```
crates/
  core/   UI 를 모르는 라이브러리
          MuPDF 래핑, 문서 모델, 텍스트 색인, 검색, 목차, 링크 목적지 해석,
          히스토리, 세션·문서 상태 저장, diff 엔진
  app/    실행 파일
          창·도킹·탭, PDF 뷰 위젯, 패널, 명령 팔레트, 입력 처리
```

`core` 는 창 없이 테스트할 수 있어야 한다. 기능의 판단 로직(히스토리 규칙, 목적지 해석, 검색 정규화, diff)은 전부 `core` 에 둔다.

### 8.2 스레드

- **UI 스레드**: egui. MuPDF 를 직접 부르지 않는다.
- **문서 워커**: 문서마다 스레드 하나가 `mupdf::Document` 를 소유한다. 요청은 채널로 받고 우선순위는
  보이는 페이지 → 미리보기 → 이웃 페이지 선렌더 → 전체 텍스트 색인 순이다.
  작업 단위(페이지) 사이마다 채널을 확인해 뒤처진 요청은 버린다.
- **결과**는 평범한 데이터(RGBA 버퍼, 텍스트·링크 구조체)로만 UI 에 넘긴다. 모든 결과에 세대 번호를 붙여 낡은 것은 버린다.
- 검색, diff, 파일 해시는 별도 백그라운드 작업이다.
- `DisplayList` 를 여러 스레드에서 래스터화하는 병렬화는 필요해졌을 때 추가한다.

### 8.3 데이터 모델

```
App
 ├─ documents: DocId → Document      (공유)
 │     경로, 내용 해시, 페이지 크기들, 목차, 페이지별 링크·텍스트(지연 로드 후 유지)
 ├─ views: ViewId → View
 │     doc, 위치, 줌 방식, 히스토리, 선택, 검색 상태
 └─ windows: [Window]
       도킹 상태(탭 = ViewId | Diff | 시작 화면), 목차 패널 상태, 크기
```

- 탭 이동(패인 간, 창 간)은 `ViewId` 를 옮기는 것뿐이다. 뷰와 문서는 그대로다.
- 위치는 `(페이지, x, y)` PDF 포인트 단위로만 저장한다. 줌이나 창 크기가 바뀌어도 같은 곳을 가리킨다.

### 8.4 캐시

- 페이지 그림: 키 `(문서 세대, 페이지, 배율, 회전)`, 바이트 예산 LRU(기본 2GB).
- 텍스트·링크·목차: 문서가 열려 있는 동안 전부 유지.
- 아주 높은 배율에서 그림이 텍스처 한계를 넘는 경우에만 보이는 영역만 잘라 렌더링한다. 타일 방식은 최적화 단계로 미룬다.

### 8.5 Diff 파이프라인

1. 양쪽 문서에서 문자 단위 텍스트와 좌표를 추출한다.
2. 잡음 제거: 여러 페이지에서 같은 위치에 반복되는 줄(숫자는 와일드카드)을 머리글·바닥글로 보고 뺀다.
3. 정규화한 비교 키를 만든다(공백, NFKC, 줄 끝 하이픈). 화면 표시는 원문 그대로.
4. 1차: 문단 단위로 문서 전체를 맞춘다. 목차 항목·절 번호 제목·양쪽에 한 번씩만 나오는 문단을 고정점으로 삼는다.
5. 2차: 바뀐 문단 쌍 안에서 단어 단위로 정제한다.
6. 각 토큰이 문자 범위를 들고 있으므로 결과를 페이지 위 사각형으로 되돌린다. 같은 줄의 인접 사각형은 합친다.
7. 일치 구간을 고정점으로 좌우 스크롤 위치를 보간한다.

## 9. 이 환경의 제약과 대응

**Wayland 네이티브로 띄운다.** GNOME 의 기본 경로다. 창 위치 복원이 요구사항이 아니므로(§7.6)
X11(XWayland) 모드를 따로 유지할 이유가 거의 없다.

Wayland 에서 툴킷(winit 0.30.13)이 못 하는 것 — 소스에서 확인:

| 제약 | 영향 | 대응 |
|---|---|---|
| 창의 화면 위치를 읽거나 정할 수 없음 | 새로 뜨는 창의 자리는 GNOME 이 정함 | 요구사항 아님. 창 크기만 복원 |
| 탭을 끄는 동안 다른 창은 포인터 이벤트를 받지 못함 | 끌어서 다른 창에 붙일 때 놓일 자리를 미리 보여 줄 수 없음 (WIN-3) | "놓은 직후 포인터가 들어온 창"을 대상으로 판정. M0 에서 실측 |
| 파일 드롭 미구현 | 파일 관리자에서 끌어다 열 수 없음 (OPEN-8) | 파일 선택기, 더블클릭, 명령줄, 최근 문서로 충분 |
| 창 숨기기 불가 | 루트 창을 숨겨 두는 우회 불가 | 아래 참조 |

WIN-3 이 끝내 쓸 만하게 되지 않으면 메뉴·단축키 경로(WIN-1, WIN-2)만 남긴다.
X11 모드는 그때 다시 검토한다(이 머신은 배율이 전부 100% 라 XWayland 로 띄워도 흐려지지는 않는다).

**루트 창 문제 (WIN-5)**: eframe 은 처음 뜬 창을 닫으면 앱이 종료된다.

1. 기본안: 처음 창을 "주 창"으로 둔다. 다른 창은 각자 닫히고, 주 창을 닫으면 저장하고 전체 종료한다.
   다음 실행 때 문서와 읽던 위치가 복원되므로 잃는 것은 없다.
2. 써 보니 불편하면: 창을 직접 관리하는 통합 코드를 써서 루트를 화면에 없는 가상 창으로 둔다(작업량 큼).

M0 에서 1 을 만들어 써 보고 판단한다.

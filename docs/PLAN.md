# refdesk 실행 계획 v0.2

요구사항 ID 는 [SPEC.md](SPEC.md), 계약(§ 번호)과 규칙(R-번호)은 [ARCHITECTURE.md](ARCHITECTURE.md) 를 가리킨다.
대상 환경은 SPEC §2 의 로컬 머신 하나다.

## 1. 역할

| 역할 | 누가 | 하는 일 |
|---|---|---|
| 설계·검수 | 상위 모델 세션 | 아키텍처와 WP 유지, 결과 검수, 마일스톤 경계에서 다음 WP 상세화 |
| 구현 | 하위 에이전트(Orca 워커) | 작업 패키지(WP) 하나를 맡아 끝까지. 기본은 Sonnet, 표에 표시된 것만 Opus |
| 확인 | 사용자 | 창을 띄워 봐야 아는 것: M0 검증, 마일스톤 완료 점검 |

비싼 모델은 설계가 바뀔 때와 마일스톤 경계에서만 쓴다. WP 를 배정하고 게이트를 돌리는 일은 낮은 모델로도 된다.

## 2. 위임 규칙

**실행 수단**: Orca 워커. WP 하나에 워커 하나를 띄우고, 워커마다 별도 채팅이 생겨 진행을 보거나 개입할 수 있다.
모델은 §3 표대로 `claude-sonnet-5-5` 또는 `claude-opus-5-5`, effort 는 `high`.

- 혼자 도는 WP 는 현재 작업 공간(`dev`)에서 일한다. 워커는 커밋하지 않고, 검수자가 검수 후 커밋한다.
- 동시에 도는 WP 는 각자 새 worktree 를 받는다. 워커는 끝에 그 브랜치에 커밋 하나를 남기고, 검수자가 검수 후 `dev` 로 병합한다.

**브리프**: 하위 에이전트는 이 대화를 모른다. 배정할 때 아래를 그대로 준다.

```
너는 refdesk 프로젝트의 WP-XX 구현자다. 저장소: /home/oscar/orca/projects/pdfToolCreation
1. 먼저 읽어라: CLAUDE.md, docs/ARCHITECTURE.md 의 §1·§2 와 <계약 절>, docs/PLAN.md 의 "WP-XX" 절.
2. 소유 파일만 만들거나 고쳐라: <목록>. 그 밖의 파일을 고쳐야 하면 멈추고 이유를 보고하라.
3. 라이브러리 API 는 기억으로 쓰지 말고 ARCHITECTURE §2.2 가 가리키는 소스를 읽어 확인하라.
4. 끝나면 scripts/check.sh 를 실행하고 통과할 때까지 고쳐라.
5. 보고: (a) 한 일 (b) 계약과 달라진 점 (c) 추가한 의존성과 이유 (d) check.sh 의 마지막 출력 (e) 못 했거나 의심스러운 것.
현재 작업 공간에서 일했으면 커밋하지 마라. 새 worktree 를 받았으면 끝에 그 브랜치에 커밋 하나를 남겨라(메시지는 영어). push 는 하지 마라.
```

**소유 파일**: WP 는 자기 소유 파일만 건드린다. 예외는 셋 — 작업 공간 `Cargo.toml` 의 의존성 추가,
`lib.rs`/`mod.rs` 의 모듈 선언 한 줄, 명령 표(`commands.rs`)에 줄 추가.

**완료 게이트**: `scripts/check.sh` = `cargo fmt --check` + `cargo clippy --workspace --all-targets -- -D warnings` + `cargo test --workspace`.

**검수**: 보고를 믿지 않는다. 게이트를 다시 돌리고 변경분을 읽는다. 규칙(R-1 ~ R-10) 위반, 소유 파일 밖의 변경,
계약과 다른 공개 시그니처는 반려한다. WP 의 "테스트" 항목이 실제로 있고 의미 있는 검사를 하는지 본다.

**병렬**: 선행이 끝났고 소유 파일이 겹치지 않는 WP 는 동시에 돌린다(한 번에 4개까지). 병합은 하나씩 하고, 병합할 때마다 게이트를 다시 돌린다.

**빌드 결과 공유**: worktree 의 워커는 `CARGO_TARGET_DIR` 로 주 작업 공간의 `target/` 을 함께 쓴다(4GB 넘는 의존성을 다시 빌드하지 않으려고).
그래서 `target/debug/refdesk` 는 **마지막에 빌드한 worktree 의 것**이다. 이 파일을 직접 실행하지 않는다
(WP-42 에서 다른 worktree 의 옛 실행 파일이 실행되어 창이 뜬 일이 있었다). 실행 파일을 확인해야 하면 `cargo run -p refdesk -- <인자>` 로,
그것도 창이 뜨지 않는 인자(`--help`, `--version`)에 한해서만 한다.

**막히면**: 같은 문제로 두 번 실패하면 우회로를 지어내지 말고 무엇이 막혔는지 보고한다.

**커밋**: 검수를 통과한 WP 하나가 커밋 하나. push 와 원격 저장소 생성은 사용자가 요청할 때만.

### WP-01 M0 검증 앱

- 소유: `spikes/m0/**` (독립 프로젝트. 버리는 코드라 구조 규칙 R-2, R-3 을 적용하지 않는다)
- 목적: SPEC §9 와 ARCHITECTURE §6 의 미확정 항목을 사용자가 직접 눌러 보고 판정할 수 있는 실험 앱.
- 할 일
  - 명령줄로 받은 PDF 를 워커 스레드에서 렌더링해 탭에 그린다(텍스처).
  - `egui_dock` 탭·분할. 창 여러 개(`show_viewport_immediate`), 창마다 도킹 상태.
  - 탭 우클릭 메뉴: "새 창으로 분리", "창 N 으로 이동".
  - 탭을 창 밖으로 끌어 놓으면 새 창으로 분리.
  - 탭을 끌어 **다른 창 위에 놓으면** 그 창에 결합: 놓은 뒤 150ms 안에 포인터가 들어온 창을 대상으로 삼는다.
    판정 근거가 되는 이벤트(어느 창이 언제 포인터 진입을 받았는지)를 화면 아래 기록 창과 표준 출력에 찍는다.
  - 주 창(처음 뜬 창)을 닫으면 전체 종료, 다른 창은 그 창만 닫힘.
  - 한글 제목의 탭과 메뉴, 한글을 입력해 볼 텍스트 칸, GNOME 파일 선택기를 여는 버튼(`rfd`).
  - 렌더링한 쪽을 `ctx.copy_image` 로 클립보드에 넣는 "이미지 복사" 버튼과, 같은 이미지를 `wl-copy --type image/png` 로 넣는 버튼.
  - 주 창에서 만든 텍스처가 다른 창에서도 그려지는지 보이게 한다(같은 문서를 두 창에).
- 완료 조건: 빌드되고, 아래 점검표를 사용자가 수행할 수 있다. 점검표를 `spikes/m0/README.md` 에 둔다.
- 사용자 점검표 (결과는 상위 모델이 SPEC §9, ARCHITECTURE §6 에 반영)
  1. 창이 뜨고 PDF 한 쪽이 보이는가. 다른 창에서도 같은 쪽이 보이는가.
  2. 메뉴로 탭을 다른 창으로 옮기고 되돌릴 수 있는가.
  3. 탭을 창 밖으로 끌어 놓으면 새 창이 생기는가. 어느 모니터에 생기는가.
  4. 탭을 다른 창 위에 끌어 놓으면 그 창에 붙는가. 10번 중 몇 번 되는가.
  5. 주 창이 아닌 창을 닫으면 그 창만 닫히는가. 주 창을 닫는 방식이 쓸 만한가.
  6. 텍스트 칸에 한글이 조합되어 입력되는가. 파일 선택기가 GNOME 것으로 뜨는가.
  7. "이미지 복사" 버튼을 누른 뒤 다른 앱(메신저, 그림 편집기)에 붙여 넣으면 이미지가 들어가는가.

1 Introduction

1.1 Purpose

This document specifies the Process Manager of the Example Platform. The Process Manager is the first user-space component that the platform starts. It launches every other application process, watches over their execution, enforces their resource limits and terminates them in an orderly way when the machine changes its operating mode or shuts down.

The intended readers are developers of platform components, integrators who write execution manifests for their applications, and test engineers who verify the platform against its requirements. Readers are expected to know POSIX process management and the basic concepts of the Example Platform described in the platform overview [EP-OVR].

1.2 Scope

The specification covers the externally visible behaviour of the Process Manager: the process lifecycle (chapter 4), resource management (chapter 5), supervision (chapter 6), error reporting (chapter 7), the client library that applications link against (chapter 8), and the execution manifest (chapter 9).

The following topics are out of scope and are covered by other documents:

  • The hardware watchdog driver and its timing. The interface the Process Manager uses is described in the Watchdog Interface Specification [EP-SWS-WDG].
  • Persistent logging and the format of log records [EP-SWS-LOG].
  • Update and installation of application packages.
  • Security policies such as capabilities and mandatory access control, apart from the identity a process is started with.

1.3 Document conventions

Requirements are written in boxes. Each requirement has a unique identifier in square brackets, a short title and a body. The identifier never changes once a requirement has been released, even if the wording is revised. A requirement that is removed keeps its identifier reserved.

[SWS_PM_00000] Example requirement

The Process Manager shall behave as stated in the body of each requirement.

Derived from: none

The key words shall, shall not, should and may are used as follows. Shall states a mandatory behaviour that is verified by a test. Should states a recommended behaviour; an implementation that deviates from it documents the reason. May states a permitted behaviour.

Code is written in monospace. Names of configuration parameters are written as startup.timeout_ms. Durations are given in milliseconds (ms) or seconds (s), memory sizes in mebibytes (MiB).

2.2 Terms

Application process
An operating system process that the Process Manager starts from an execution manifest. A program may be started as several application processes with different arguments.
Execution manifest
The configuration file that tells the Process Manager how to start a program: its path, arguments, environment, identity, dependencies and limits. See chapter 9.
Function group
A named set of application processes that are started and stopped together. A machine has several function groups; each is in exactly one of its states at a time.
Function group state
A named configuration of a function group, for example Off, Driving or Diagnostics. It lists the processes that run in it.
Grace period
The time a process is given to exit after it has been asked to terminate, before it is killed.
Reported state
The state that an application process announces to the Process Manager through the client library, as opposed to the state the Process Manager observes from the operating system.
Supervision
The checks the Process Manager performs on a running process to find out whether it still makes progress. See chapter 6.

3 Architecture

3.1 Overview

The Process Manager runs as a single daemon, ep-pm, that the init system starts early during boot. It reads all execution manifests, computes the order in which processes must be started, and from then on reacts to three kinds of events: requests to change a function group state, state reports from application processes, and exit notifications from the operating system.

[SWS_PM_00001] Single instance

Exactly one Process Manager shall run on a machine. A second instance that is started while the first one is running shall exit with status 1 without starting any process.

Derived from: EP-OVR-0031

[SWS_PM_00002] Start before applications

The Process Manager shall be the parent of every application process. Application processes shall not be started by the init system directly.

Derived from: EP-OVR-0032

Internally the Process Manager consists of four parts. The manifest loader parses and validates execution manifests. The state engine owns the function group states and decides which processes have to start or stop. The launcher creates processes, applies their identity and limits, and collects their exit status. The supervisor runs the checks described in chapter 6 and reports failures to the state engine.

3.2 Process model

3.2.1 Process states

The Process Manager keeps one state machine per application process. The states and the transitions between them are shown in Figure 1. A process enters Starting when the launcher has created it, and Running when it reports that its initialisation is complete ([SWS_PM_00020]). Any exit, whether requested or not, leads to Terminated.

The Failed state is entered when a supervision check fails while the process is running. The Process Manager then terminates the process in the same way as a requested termination, except that the reason is recorded as a failure and the restart policy of 4.2.2 applies.

StateMeaningLeft when
IdleThe process is configured but not started.Its function group enters a state that lists it.
StartingThe process exists and initialises itself.It reports kRunning, exits, or the startup timeout expires.
RunningThe process has reported that it is ready.It is asked to terminate, exits, or fails a check.
TerminatingThe process has been asked to exit.It exits or the grace period expires.
TerminatedThe process has exited and has been reaped.It is started again.

3.2.2 Function groups

Every application process belongs to exactly one function group. A function group has a set of named states, and each state lists the processes that run while the group is in it. The special state Off exists in every function group and lists no processes.

[SWS_PM_00005] Initial function group state

At start, the Process Manager shall put every function group into the state named by its initial_state parameter, or into Off if the parameter is absent.

Derived from: EP-OVR-0040

[SWS_PM_00006] State change

On a request to change a function group to another state, the Process Manager shall terminate the processes that are not listed in the new state, then start the processes that are listed in the new state and are not running. Processes listed in both states shall keep running.

Derived from: EP-OVR-0041

A state change completes when every process to be stopped has reached Terminated and every process to be started has reached Running. The result is reported to the requester through StateClient::SetState (8.4).

3.2.3 Execution dependencies

A process may depend on other processes of the same function group. A dependency names the other process and the state it must have reached, either Running or Terminated. A dependency on Terminated is used for one-shot setup programs that must finish before the dependent process starts.

[SWS_PM_00008] Dependency order

The Process Manager shall not start a process before all processes it depends on have reached the state required by the dependency.

Derived from: EP-OVR-0045

[SWS_PM_00009] Dependency cycles

The manifest loader shall reject a set of manifests whose dependencies form a cycle. The error shall name every process on the cycle.

Derived from: EP-MAN-0012

Processes without a dependency between them may be started in parallel. Termination follows the reverse order: a process is asked to terminate only after every process that depends on it has terminated.

4 Process lifecycle

4.1 Startup

4.1.1 Startup sequence

For each process to start, the launcher performs the following steps in this order. A failure in any step ends the start attempt; the process goes to Terminated and the error is reported as kStartFailed (7.2).

  1. Create the process with fork or posix_spawn.
  2. Place the process into its resource group (5.1).
  3. Apply the resource limits of 5.2.
  4. Switch to the user and group identity of the manifest.
  5. Set the working directory and replace the environment.
  6. Execute the program with the arguments of the manifest.

[SWS_PM_00012] Start order

Within one state change, the Process Manager shall start processes in an order that satisfies all execution dependencies ([SWS_PM_00008]). Among processes that are ready to start at the same time, it shall start them in ascending order of their startup.priority.

Derived from: EP-OVR-0045, EP-OVR-0046

[SWS_PM_00013] Environment

A started process shall receive only the environment variables listed in its manifest, plus EP_PROCESS_NAME and EP_FUNCTION_GROUP. The environment of the Process Manager itself shall not be inherited.

Derived from: EP-OVR-0050

[SWS_PM_00014] Open file descriptors

A started process shall have only standard input, standard output and standard error open, connected as configured in stdio. All other descriptors of the Process Manager shall be closed before the program is executed.

Derived from: EP-OVR-0051

4.1.2 Startup timeout

A process that does not report kRunning in time is considered hung. The startup timeout starts when the program has been executed, not when the process was created, so that slow resource group setup does not count against the process.

[SWS_PM_00016] Startup timeout

The Process Manager shall terminate a process that has not reported kRunning within 5 s after it was executed, and report kStartTimeout.

The Process Manager shall terminate a process that has not reported kRunning within the startup timeout configured in its manifest (startup.timeout_ms, default 3000 ms) after it was executed, and report kStartTimeout.

Derived from: EP-OVR-0052

[SWS_PM_00017] Termination after timeout

A process terminated because of a startup timeout shall be terminated as described in 4.3.1, including its grace period.

Derived from: EP-OVR-0052

Integrators should measure the startup time of each process on the slowest supported hardware and set startup.timeout_ms to at least twice that value. A timeout that is too short makes the process fail on a busy machine and causes restarts that slow the machine down further.

4.2 Running

4.2.1 State reporting

An application process reports its own progress through the client library (8.3). The report is the only way for the Process Manager to learn that a process has finished its initialisation; the existence of the operating system process alone is not enough.

[SWS_PM_00020] Running report

When a process in Starting reports kRunning, the Process Manager shall move it to Running and start every process whose dependencies are now satisfied.

Derived from: EP-OVR-0053

[SWS_PM_00021] Unexpected reports

A report that does not fit the current state of the process, such as kRunning from a process in Running, shall be ignored and logged at warning level. The call shall return kInvalidTransition to the caller.

Derived from: EP-OVR-0053

Reports are delivered over a per-process IPC channel that the launcher creates before the program is executed. The channel is identified by the descriptor number in the environment variable EP_PM_CHANNEL; it is the only descriptor that is kept open in addition to the standard streams of [SWS_PM_00014].

4.2.2 Restart policy

A process that exits while its function group state still lists it has exited unexpectedly. What happens next is decided by the restart policy in its manifest.

PolicyBehaviour
neverThe process stays in Terminated. The function group remains in its state; the failure is reported.
on-failureThe process is started again if it exited with a non-zero status, was killed by a signal or failed a supervision check.
alwaysThe process is started again after every unexpected exit.
Table 5: Restart policies

[SWS_PM_00024] Restart limit

The Process Manager shall restart a process at most restart.max_attempts times within restart.window_s. When the limit is reached, it shall leave the process in Terminated and report kRestartLimit.

Derived from: EP-OVR-0060

[SWS_PM_00025] Dependents of a restarted process

Before a process is restarted, the processes that depend on it being Running shall be terminated. They shall be started again once the restarted process has reached Running.

Derived from: EP-OVR-0061

Restarting a process immediately after it has failed tends to fail again for the same reason, for example when a server it connects to is still starting. Version 1.1 therefore adds a delay between attempts that grows with every failure.

[SWS_PM_00026] Restart back-off

The Process Manager shall wait before each restart attempt. The first delay is restart.delay_ms; each further delay within the same window is twice the previous one, up to restart.max_delay_ms.

Derived from: EP-OVR-0062

4.3 Termination

4.3.1 Requested termination

A process is asked to terminate when its function group leaves a state that lists it, when the machine shuts down, or when a supervision check fails. The process is expected to release its resources, report kTerminating and exit with status 0.

[SWS_PM_00030] Termination signal

To ask a process to terminate, the Process Manager shall send it SIGTERM and move it to Terminating.

Derived from: EP-OVR-0070

[SWS_PM_00031] Grace period

The Process Manager shall give a terminating process termination.grace_ms to exit. The grace period starts when SIGTERM is sent.

Derived from: EP-OVR-0071
// Typical handling of SIGTERM in an application process.
static std::atomic<bool> stop_requested{false};

extern "C" void on_sigterm(int) { stop_requested = true; }

int main() {
    std::signal(SIGTERM, on_sigterm);
    ep::pm::ProcessClient client;
    Server server = Server::Open();
    client.ReportState(ep::pm::ProcessState::kRunning);

    while (!stop_requested) {
        server.Poll(std::chrono::milliseconds(100));
    }

    client.ReportState(ep::pm::ProcessState::kTerminating);
    server.Close();
    return 0;
}

4.3.2 Forced termination

If a process does not exit within its grace period, it is killed. A process that has been killed cannot clean up, so integrators should choose a grace period that covers the slowest expected shutdown.

[SWS_PM_00033] Kill after grace period

When the grace period of a terminating process expires, the Process Manager shall send SIGKILL to every process in its process group and report kKilled.

Derived from: EP-OVR-0072

[SWS_PM_00034] Orphaned children

Processes created by an application process shall be terminated together with it. The Process Manager shall use the resource group of 5.1 to find them, not the parent relation, because a child may have been re-parented.

Derived from: EP-OVR-0073

5 Resource management

5.1 Resource groups

Each application process runs in its own resource group, implemented as a control group of the operating system. The resource group holds the process and every process it creates. Limits are set on the resource group, so they apply to the program as a whole and cannot be escaped by creating children.

[SWS_PM_00040] One group per process

The launcher shall create a resource group named after the function group and the process, ep/<function-group>/<process>, and place the new process into it before the program is executed.

Derived from: EP-OVR-0080

[SWS_PM_00041] Removal

The resource group shall be removed after the last process in it has exited.

Derived from: EP-OVR-0080

6 Supervision

Supervision finds processes that still exist but no longer do their work, for example because they are stuck in a loop or wait forever on a lock. Each check is configured per process. A failed check moves the process to Failed (Figure 1).

6.1 Alive supervision

Alive supervision checks that a process calls ProcessClient::ReportAlive regularly. The expected interval and the tolerated deviation are set in the manifest.

[SWS_PM_00050] Alive check

For a process with supervision.alive_interval_ms set, the supervisor shall count the alive reports in each interval. If the count is below supervision.alive_min or above supervision.alive_max in supervision.alive_failures consecutive intervals, the check fails.

Derived from: EP-OVR-0090

[SWS_PM_00051] Start of alive supervision

Alive supervision of a process shall start when the process reaches Running and stop when it leaves Running.

Derived from: EP-OVR-0090

6.2 Deadline supervision

Deadline supervision checks the time between two checkpoints in the code. A process marks the start and the end of a monitored section with ReportCheckpoint; the supervisor compares the elapsed time with the minimum and maximum of the manifest.

[SWS_PM_00053] Deadline check

For each configured pair of checkpoints, the supervisor shall fail the check if the end checkpoint is reported earlier than min_ms or later than max_ms after the start checkpoint, or not at all within max_ms.

Derived from: EP-OVR-0091
# Deadline supervision in the execution manifest
[[supervision.deadline]]
name     = "frame"
start    = 10        # checkpoint id reported before the work
end      = 11        # checkpoint id reported after the work
min_ms   = 2
max_ms   = 40

6.3 Logical supervision

Logical supervision checks that checkpoints are reported in an allowed order. The manifest describes the allowed order as a graph: each checkpoint lists the checkpoints that may follow it. This finds processes that skip a step of their work, for example a control loop that publishes results without reading new input.

[SWS_PM_00056] Logical check

For a process with a supervision.logical graph, the supervisor shall fail the check when a checkpoint is reported that is not a successor of the previously reported checkpoint in the graph.

Derived from: EP-OVR-0093

[SWS_PM_00057] Graph entry

The first checkpoint after the process reaches Running shall be one of the entry checkpoints of the graph; any other checkpoint fails the check.

Derived from: EP-OVR-0093
# Logical supervision: read (20) must come before compute (21) and publish (22)
[supervision.logical]
entry = [20]
edges = { 20 = [21], 21 = [22], 22 = [20] }

6.3 Interaction with the watchdog

6.4 Interaction with the watchdog

The supervisor services the hardware watchdog through the interface of [EP-SWS-WDG]. As long as all supervised processes pass their checks, the watchdog is triggered regularly. If the Process Manager itself stops working, the watchdog is no longer triggered and resets the machine.

[SWS_PM_00059] Watchdog service

The supervisor shall trigger the watchdog at the interval returned by WatchdogClient::GetTimeout divided by three. It shall stop triggering only when a process whose manifest sets supervision.critical = true fails a check and cannot be restarted.

Derived from: EP-OVR-0095, EP-SWS-WDG SWS_WDG_00004
Note: The watchdog timeout is fixed by the hardware and read once at start. See chapter 3 of [EP-SWS-WDG] for the supported timeouts.

7 Error handling

7.1 Error classification

Errors are divided into three classes. Configuration errors are found by the manifest loader before any process is started; they stop the affected function group from entering the requested state. Process errors concern one application process and are handled by the restart policy. Platform errors concern the Process Manager itself, for example a failure to create a resource group, and are reported to the platform health monitor.

[SWS_PM_00062] Error reporting

Every error shall be logged with its code from 7.2, the process name, the function group and, for process errors, the exit status or signal.

Derived from: EP-SWS-LOG SWS_LOG_00010

8 API reference

8.1 Header and namespace

The client library is a C++17 library. All declarations are in the namespace ep::pm and in the header <ep/pm/client.h>. The library is thread-safe: every function may be called from any thread. Functions do not throw; errors are returned as ErrorCode.

8.2 Types

namespace ep::pm {

enum class ProcessState : std::uint8_t {
    kRunning     = 0,  // initialisation complete
    kTerminating = 1,  // about to exit
};

enum class ErrorCode : std::int32_t {
    kOk = 0, kInvalidManifest = 1, kDependencyCycle = 2, kStartFailed = 3,
    kStartTimeout = 4, kKilled = 5, kMemoryLimit = 6, kSupervisionFailed = 7,
    kRestartLimit = 8, kResourceGroup = 9, kInvalidTransition = 10,
};

using CheckpointId = std::uint32_t;

}  // namespace ep::pm

8.3 ProcessClient

ProcessClient is used by an application process to talk about itself. Each process creates at most one instance, usually at the start of main.

class ProcessClient {
public:
    // Connects to the channel named by EP_PM_CHANNEL.
    ProcessClient();

    // Reports the state of the calling process (4.2.1).
    ErrorCode ReportState(ProcessState state);

    // Alive supervision (6.1). Cheap; may be called from a hot loop.
    void ReportAlive();

    // Deadline and logical supervision (6.2, 6.3).
    void ReportCheckpoint(CheckpointId id);
};

[SWS_PM_00070] Constructor without channel

If EP_PM_CHANNEL is not set, the constructor shall create a client whose functions do nothing and return kOk, so that a program can also run outside the platform.

Derived from: EP-OVR-0100

[SWS_PM_00071] Non-blocking reports

ReportAlive and ReportCheckpoint shall not block. If the channel is full, the report shall be dropped and counted; the count is sent with the next report that fits.

Derived from: EP-OVR-0101

[SWS_PM_00072] Time stamps

Each report shall carry a time stamp of the monotonic clock taken in the calling thread, so that the supervisor measures the time of the call and not the time of delivery.

Derived from: EP-OVR-0101

8.4 StateClient

StateClient is used by the platform component that decides the operating mode of the machine, to change function group states. Its use is restricted to processes whose manifest sets permissions.state_control = true.

class StateClient {
public:
    StateClient();

    // Requests a state change (SWS_PM_00006) and waits for its result.
    ErrorCode SetState(std::string_view function_group,
                       std::string_view state,
                       std::chrono::milliseconds timeout);

    // The current state of a function group, or an empty string if unknown.
    std::string GetState(std::string_view function_group) const;
};

[SWS_PM_00075] Concurrent requests

If a state change of a function group is requested while another change of the same group is in progress, the Process Manager shall finish the first change before starting the second one. Requests for different function groups may run in parallel.

Derived from: EP-OVR-0105

9 Configuration

9.1 Manifest format

Execution manifests are TOML files in /etc/ep/manifests/, one file per program. A file may define several processes of the same program. The schema is defined in [EP-MAN]; the example below shows the parameters used in this document.

# /etc/ep/manifests/telemetry.toml
[program]
path = "/opt/ep/bin/telemetry"
user = "telemetry"

[[process]]
name           = "telemetry-collector"
function_group = "Machine"
states         = ["Driving", "Diagnostics"]
arguments      = ["--mode", "collect"]
environment    = { RUST_LOG = "info" }
depends_on     = [{ process = "time-sync", state = "Running" }]

  [process.startup]
  priority   = 20
  timeout_ms = 4000

  [process.restart]
  policy       = "on-failure"
  max_attempts = 3
  window_s     = 60
  delay_ms     = 250
  max_delay_ms = 8000

  [process.limits]
  memory_mib  = 192
  cpu_percent = 50

[SWS_PM_00080] Unknown parameters

The manifest loader shall reject a manifest that contains a parameter not defined in [EP-MAN], naming the file, the line and the parameter.

Derived from: EP-MAN-0003

[SWS_PM_00081] Reloading

On SIGHUP, the Process Manager shall read the manifests again. Changes shall apply to processes started after the reload; running processes shall keep the configuration they were started with.

Derived from: EP-MAN-0004
